# 架构与关键流程

## 服务职责

Python 服务负责理解问题、选择工具、检索规则与校验回答；Java 服务负责登录身份、名额与订单状态的最终判断。模型不能用知识库或旧消息替代实时接口数据。

`frontend` 的 `/api/` 请求转发 Java，`/ai/` 转发 Python。token 仅保留在 Vue 内存中，每次私有请求单独携带，Python 不共享用户令牌。

## Agent 路由

入口位于 `ai-service/assistant_api/conversation_service.py`。普通消息经过两次结构化调用：补全独立问题、检查补全后的意图。图定义位于 `agent_service.py`，包含规则、活动列表、活动详情、本人订单、混合查询和澄清路径。

活动列表的 `event_filter` 有三种值：

| 值 | 程序判断 |
| --- | --- |
| all | 全部公开已发布活动 |
| not_ended | 报名截止时间晚于本次查询时刻 |
| open | 已到报名开始时间、尚未截止且有剩余名额 |

查询时刻来自 MCP 工具返回的 `queried_at`；时区或日期异常时拒绝作出时间判断。活动处于可报名时段不代表某用户一定能成功创建订单，最终仍由 Java 事务决定。

## RAG

`retrieval_service.py` 按 Markdown 二级标题拆分完整规则小节，使用 BGE 向量与 BM25 并行召回，通过 RRF 融合后交给 Cross-Encoder 重排。模型在 CUDA 上加载，Qdrant 当前为本地持久化模式。

知识内容、模型与拆分方式参与索引版本计算，避免规则更新后无意复用旧索引。回答采用结构化 claims/evidence：程序逐字检查引用，模型再检查依据支持程度与问题覆盖。检查不通过时不输出候选业务结论。

## 上下文与记忆

完整 messages 的预算同时计入系统提示、JSON Schema、当前问题和历史。应用预算采用近似计数，真实用量以模型 API usage 为准。近期历史按完整轮次从新到旧选择，遇到不能容纳的轮次就停止。

较早历史摘要最多扫描 100 轮、保留 4 条不超过 160 字符的完整用户原话，保存来源轮次并逐字校验。摘要在近期历史之后使用剩余预算，不能作为新操作授权。长期偏好只持久化 concise/plain，当前表达要求可单次覆盖。

## 报名幂等与恢复

1. 前端识别明确报名表达，为新操作生成 32 位十六进制编号，先保存待确认请求再发送。
2. Python 先确认会话归属，并根据本次原始消息进入报名节点，跳过模型改写。操作意图在请求 Java 前提交到 SQLite。
3. Java 通过 `(user_id, operation_id)` 唯一键和事务锁定操作记录，同一操作不能更换活动。
4. 首次成功创建订单并保存映射；成功映射已存在时返回原订单当前状态，包括取消或过期后的状态。
5. 结果未知或历史保存失败后，调用方保留原编号重试，不生成新的编号。取消后真正重新报名需要新操作编号。

拒绝结果不永久缓存；不能将该方案理解为任意故障下的全局 Exactly-once。

## Java 名额与订单

名额预留使用带时间与余量条件的 SQL 更新。订单插入与名额扣减处于同一事务中；有效订单的生成列唯一约束限制同一用户对同一活动的重复有效报名。异常时整个事务回滚。

模拟支付、取消与过期都通过条件状态更新竞争，只有成功改变状态的路径才归还名额。RabbitMQ 通过 TTL/死信触发到期检查，数据库定时扫描负责兜底。

## Redis 缓存

公开活动详情采用 cache-aside，包含短期空值缓存和有效值 TTL 抖动。单 JVM 中按活动编号加锁、锁内二次检查，减少并发冷启动回源。报名、取消、实际过期归还和发布活动后，通过事务提交后事件使详情缓存失效。

缓存不承担报名库存扣减；MySQL 仍是写入判断依据。当前请求合并不是分布式锁，缓存可能短时陈旧。
